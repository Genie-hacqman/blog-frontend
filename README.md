# Blog Frontend

React + Vite (JSX) client for [Blog-api](../Blog-api).

## Setup

```sh
npm install
cp .env.example .env   # leave VITE_API_URL empty: the dev server proxies /api to http://localhost:3030 (Blog-api's default PORT)
npm run dev            # http://localhost:5173 (proxies /api and /media to the API)
```

`VITE_API_URL` is baked in at build time. Empty (the default) means same-origin `/api`; set a full origin only to call an API directly. `npm run build` fails if it is not defined at all.

### Production: proxy `/api` through the frontend host

The API's refresh-token cookie is `HttpOnly` and scoped to `/api/auth`. For it to survive in every browser (Safari blocks cross-site cookies) the browser must talk to the API through the frontend's own domain. On Vercel, add a rewrite **before** the SPA catch-all in `vercel.json` (replace the host with the API's production origin, and add this site's origin to `CLIENT_ORIGIN` on the API):

```json
{
  "rewrites": [
    { "source": "/api/:path*", "destination": "https://YOUR-API-HOST/api/:path*" },
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}
```

Then build with `VITE_API_URL` set to an empty value.

The API must allow this origin via `CLIENT_ORIGIN` in `Blog-api/.env` (defaults to `http://localhost:5173`).

## Structure

- `src/api/` — `fetch` wrapper (`client.js`) and endpoint functions; `request()` unwraps the API's `{ success, data }` envelope and throws `ApiError(status, message, code)`. The access token is kept in module memory only; on a 401 the client refreshes once (shared between concurrent requests, using the HttpOnly cookie) and retries
- `src/auth/` — `AuthProvider` (user in state; a non-secret `blog.session` hint in localStorage triggers a silent refresh on reload; logout or a lost session clears the query cache), `useAuth`, `ProtectedRoute` (waits while a session is being restored)
- `src/pages/ProfilePage.jsx` (`/u/:username`, public) and `SettingsPage.jsx` (`/settings`: profile photo, bio and links, password link, account deletion). Profile text is always rendered as text, and links only if they are plain `https://`
- `src/components/Avatar.jsx`, `AuthorName.jsx` — photo (or initial) and the linked author name used in bylines; deleted authors render as plain "Deleted user"
- `src/hooks/useProfile.js` — profile queries and mutations (photo upload is multipart `FormData`; the server re-encodes it)
- Post lifecycle: `PostPage` serves the public article at `/blog/:slug` (`by="slug"`) and the private preview at `/posts/:id` (`by="id"`, which sends a published post on to its public address). `PostActions` shows only the status moves the API lists in `post.actions` (submit, withdraw, approve, reject with a reason, schedule, publish, archive...); the server still decides. `NewPostPage` and `EditPostPage` save drafts (a post waiting for review, scheduled or archived is read-only until the author withdraws it). `MyPostsPage` (`/me/posts`) is the author's dashboard, `ReviewQueuePage` (`/review`, editors and admins) the queue, `RevisionsPage` (`/posts/:id/revisions`) compares versions line by line and restores one (`DiffView`). `RequireRole` only hides pages from people who cannot use them; the API enforces every permission.
- Writing: `PostForm` holds a rich text editor (`RichTextEditor` with `EditorToolbar`, built on TipTap). It is loaded on demand (`React.lazy`), so readers never download it. It offers headings (H2 to H4), bold, italic, strikethrough, inline code, links (http(s) and email only), bulleted and numbered lists, quotes, code blocks with a language, rules, undo/redo, and pictures (button, drag-and-drop or paste; uploaded to `POST /api/media` as `inline`, with a description field for the selected picture). Write / Preview shows the story exactly as `ContentView` will render it. `CoverImageField` uploads the picture above the title (`cover`) with its description. On the edit page an unpublished story saves itself 5 seconds after the writer stops typing (`useAutosave`): every save, automatic or by button, goes through one queue and names the version it started from (`expectedUpdatedAt`), so a save from another tab is reported (`EDIT_CONFLICT`) instead of overwritten. A published story is never saved automatically. Code colours come from `lowlight` (loaded only when a page has a code block, and built from DOM nodes, never from an HTML string).
- Community: under every published story `ReactionBar` (like and save, with counts; signed-out readers get log-in links instead of dead buttons) and `CommentSection` (a form, then the comments a page at a time with "Load more"). Comments are **plain text**, rendered as text with preserved line breaks, never through `ContentView` and never with clickable links. `CommentItem` offers Reply (top-level comments only: one level of replies, loaded on demand), Edit and Delete (with a confirmation) according to `canEdit`/`canDelete`, which the API decides; a deleted comment with replies shows as a placeholder. Posting needs a verified email (others see why) and carries an `Idempotency-Key`, so a double click or a retry posts once. Likes, saves and follows are **optimistic** (`src/hooks/useEngagement.js`): the button changes at once, the server's answer replaces the guess, a failure puts everything back and shows the reason. `ProfilePage` shows follower and following counts and a `FollowButton`; `PeoplePage` (`/u/:username/followers|following`), `FeedPage` (`/feed`, "Following") and `BookmarksPage` (`/me/bookmarks`, "Saved") list people and stories. Cards show like and comment counts when there are any.
- Notifications: `NotificationBell` (in the navbar for signed-in readers) shows the number of unread notifications; `useUnreadCount` asks the API every minute while the tab is open and again when the reader returns to it (there is no push channel yet). `NotificationsPage` (`/notifications`) is the inbox: All / Unread, "Mark all as read", "Load more", Dismiss on each row. Opening a notification marks it read; marking and dismissing are **optimistic** (the badge changes at once and goes back, with the reason, if the server refuses; see `src/hooks/useNotifications.js`). Names, story titles and comment excerpts come from the API as plain text and are rendered as text. What each kind says and where it leads is in `NotificationItem` (add a kind there when the API adds one). `NotificationPreferences` (in Settings) is a grid of kinds by "In the inbox" / "By email". `UnsubscribePage` (`/unsubscribe?token=`) is where the link in a notification email lands: it explains what will happen and changes nothing until the button is pressed.
- Moderation and administration: `ReportButton` / `ReportForm` appear under another person's comment, story and profile (a signed-out visitor is sent to log in; your own things never show it). Reports are filed with a reason from a fixed list and optional plain-text details, once per thing (a second try says so kindly), and never act by themselves. `ModerationQueuePage` (`/moderation`, editors and admins) shows each reported thing once with how many people reported it and why, who reported it on request, and the decision buttons (Dismiss, Remove comment, Unpublish story, and Suspend account for admins, who alone see reports about people); every decision but Dismiss needs a note and a confirmation step, and the note is shown to the author. The admin area (`/admin`, admins only; the server enforces it, `RequireRole` only hides it): `AdminDashboardPage` (counts, where something needs a person, recent activity in plain words), `AdminUsersPage` (search by username or email start, filters, role change, suspend with a required reason, reinstate, sign out everywhere; an admin cannot suspend or re-role themselves) and `AuditLogPage` (filters, readable lines from `src/lib/audit.js`, with the exact action beside each). Every user-supplied string here (reasons, notes, excerpts) is rendered as plain text.
- Sections, topics and search: `SectionNav` (the strip under the masthead; sections with no published story are left out) and `SearchBox` are in the header. `TaxonomyPage` serves `/category/:slug` and `/tag/:slug`, `SearchPage` serves `/search?q=` (the query, section filter, order and page all live in the address, so a search can be shared). `ManageCategoriesPage` (`/manage/categories`, editors and admins) creates, renames and deletes sections; renaming never changes a section's address. In the editor, `PostForm` has a section picker and `TagInput` (Enter or comma adds a tag, up to 5, suggestions from existing tags); the edit page sends the section and tags only when they changed. `TagChips` and the section kicker link posts to their pages. Hooks are in `src/hooks/useTaxonomy.js` (the section list is cached for 5 minutes).
- Analytics: the public story page (`PostPage by="slug"`, never the private preview) calls `useTrackStory`, which sends one "view" message after the story has been on screen for 1.5 seconds and one "reading" message (seconds the tab was visible, deepest point scrolled to) when the reader leaves or hides the tab, through `beacon()` in `src/api/client.js` (`fetch` with `keepalive`; it never throws and never retries). It is switched off for the author's own story, an unpublished story and while it is not yet known who is looking, so the author's visits are never counted by mistake. Nothing is stored in the browser and no identifier is sent: the server tells visitors apart within one day only, with a key that changes daily (see the API's `CLAUDE.md`). `MyStatsPage` (`/me/stats`, authors and up), `StoryStatsPage` (`/posts/:id/stats`) and `AdminAnalyticsPage` (`/admin/analytics`) show the numbers with a 7/30/90-day switch; `BarChart` is plain SVG with a text summary and a "Show as table" toggle, so no figure depends on seeing the picture, and `HowWeCount` explains what each number means (visitors are counted per day and added up; a "read" needs most of the story scrolled and a believable time). Referrer hostnames come from the API and are rendered as text.
- Search engines and link previews: every page describes itself with `useSeo` (`src/seo/useSeo.js`; the tags are owned by `src/seo/manager.js`): title, description, canonical address (none on a page that is not indexed), robots, Open Graph, Twitter, article tags and JSON-LD (`src/seo/site.js` builds the schema.org data and mirrors the API's crawler snapshots). Pass `null` while the page does not know yet. Tags are replaced when the page changes and removed when it goes away, and what `index.html` shipped comes back. A page that is private is marked with `<NoIndex />` (done once for everything behind `ProtectedRoute` and for the sign-in pages); a page that describes itself overrides it. The app answers `200` for any address, so `NotFoundPage` marks itself `noindex`. Only the public page of a published story is indexed (the private preview, drafts and archived stories are not); a section, topic or profile with nothing published is `noindex,follow`; search results are `noindex,follow`.
- Crawlers that do not run JavaScript (Slack, WhatsApp, Facebook, X, LinkedIn, Discord ...) cannot read any of that, so the host sends them to the API's plain-HTML snapshots instead (`/api/seo/...`, same content, real 404s, no scripts). **This needs a host rewrite you must install**: copy the rules of `vercel.seo.example.json` into `vercel.json`, in that order and before the final catch-all, after replacing `YOUR-API-HOST` with the API's origin (the `/api` rule is the same one described under Setup). They also serve `/robots.txt`, `/sitemap.xml` and the RSS feeds (`/feed.xml`, `/feed/author|category|tag/<name>.xml`) from the API, so every address points at this site. On another host the contract is the same: API paths first, then `robots`, sitemaps and feeds, then the five public page types for crawler user agents, then the app. After deploying, check a story with the Facebook Sharing Debugger, the LinkedIn Post Inspector and Google's URL Inspection, and submit `/sitemap.xml` in Search Console. `public/og-default.png` is the picture shown when a story has no cover (regenerate it with `node scripts/make-og-default.mjs "<name>" "<tagline>"` in Blog-api if the publication is renamed; set the API's `SITE_NAME`, `SITE_TAGLINE`, `SITE_DESCRIPTION` to match `src/components/site.js`).
- Security: `vercel.json` sends protective headers on every page (`nosniff`, `X-Frame-Options: DENY`, a strict referrer policy, a permissions policy that switches off camera, microphone, location, payment and USB, HSTS, `Cross-Origin-Opener-Policy`) and a **`Content-Security-Policy-Report-Only`**: scripts only from this site (no inline script, no `eval`; the theme script is the file `public/theme-init.js` for that reason), styles from this site and Google Fonts (`'unsafe-inline'` stays for styles because the editor adds a `<style>` element), pictures from this site and any https host (uploads live on the storage domain), no plugins, no framing. Violations are posted to the API (`/api/security/csp-report`, which needs the `/api` rewrite) and appear in its log as `Content-Security-Policy violation reported`. **Move to enforcing** after a week without unexpected reports: rename the header to `Content-Security-Policy` in `vercel.json`. If `VITE_API_URL` is not empty (the app calls the API directly), add that origin to `connect-src` first, or every request will be reported (and, once enforced, blocked). `src/lib/safeRedirect.js` limits where signing in may send you back to (only a path on this site). Settings has "Where you are signed in" (`SessionsSection`): the devices that are signed in, a way to end any other one (optimistic, with rollback), and "Sign out everywhere". New passwords are checked by the API (common, trivial or containing your name or email are refused); the forms say so in a hint. CI fails on a high or critical `npm audit` finding and scans for committed secrets.
- `src/hooks/usePosts.js` — TanStack Query hooks; mutations invalidate `['posts']`
- `src/schemas/` — Zod form schemas mirroring the API's validation
- `src/pages/`, `src/components/` — UI (Tailwind)

Post bodies are HTML written in the editor and are **only ever shown through `ContentView`**, which sanitizes them with DOMPurify (`src/lib/sanitizeHtml.js`: an allowlist that mirrors the API's, http(s)/mailto links with a forced `rel`, pictures only from http(s) or this site, no scripts, handlers, styles or `data:` URLs) every time, on top of the API sanitizing them when they are saved. Never use `dangerouslySetInnerHTML` anywhere else, and never render post HTML that did not come through `sanitizeHtml`. The access token is not in localStorage.
